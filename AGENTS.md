# AGENTS.md: PitchPrep

> Place this file at the repository root. It is the main instruction file for the coding agent (Codex).

## What we are building

**PitchPrep** is a multi-agent sales research assistant. A user gives a company name plus its website (or social) link, and the system returns a source-backed prospect brief and an email draft, with every claim checked by a Verifier agent.

**Read `docs/PRD.md` first.** It is the source of truth for scope, user flow, the agent pipeline, data model, and acceptance criteria. If this file and the PRD ever disagree on product behavior, follow the PRD and tell Hamza about the conflict.

Stack: Next.js (frontend), FastAPI + LangGraph (backend), Firecrawl, Groq models, Supabase, LangSmith.

## Hard rules (never break these)

1. **Never push to GitHub.** Do not run `git push` in any form, do not open or merge pull requests, and do not change git remotes or git config. Hamza reviews all work and pushes it himself.
2. **Do not commit unless asked.** Leave changes in the working tree so Hamza can review the diff. If he asks for a commit, make a local commit only.
3. **Never commit or print secrets.** No API keys, tokens, or `.env` contents in code, logs, docs, or chat. Keep `.env*` files in `.gitignore` and maintain an `.env.example` with variable names only. The Supabase service-role key lives only on the backend and must never reach the frontend.
4. **Stay inside the PRD scope.** Do not add batch/CSV processing, automatic email sending, user accounts, CRM integrations, or named-contact scraping. If something seems necessary but is not in the PRD, ask first.
5. **Never fabricate.** No invented facts, URLs, statistics, testimonials, customer logos, or test results. Do not claim tests or builds passed unless you ran them and saw them pass.

## MCP: Supabase

A Supabase MCP server is configured in this project environment.

- Before any write, confirm which Supabase project the MCP is connected to. Use the development project. Never write to production without Hamza's explicit approval.
- Always use Supabase MCP for agent-performed database operations, including schema inspection, queries, table creation, schema changes, and policy updates.
- Apply authorized changes directly to Supabase through MCP. Do not create local files in `supabase/migrations/` when MCP is available.
- If the MCP connection fails, explicitly inform Hamza of the failure and which operation could not be completed. Do not silently switch to another database connection method or claim the operation succeeded.
- Only when MCP is unavailable, create a fallback SQL file in `supabase/migrations/` if needed. Clearly mark it as unapplied and tell Hamza where it is saved.
- After applying changes through MCP, verify the resulting schema, policies, or data and report what changed.
- Ask before destructive operations: dropping tables or columns, truncating tables, deleting data, or disabling row level security.
- Keep row level security enabled. Application database access goes through the backend; development agents use Supabase MCP.

## Frontend requirements

- **The home page (`/`) is intro-first.** Hero section, a "how it works" section, a trust/verification section, and a closing call. A single **centered primary button** (label: "Let's prep your pitch") takes the user to the workflow at `/app`. Do not put the input form, seller setup, or any agent UI on `/`.
- Use Next.js App Router, TypeScript, and Tailwind as already configured.
- Responsive from 360px wide, keyboard accessible, visible focus states, respects `prefers-reduced-motion`.
- Handle loading, empty, and error states on every screen.
- No placeholder copy, fake logos, or invented metrics.
- Run `npm run lint` and `npm run build` in `frontend/` before reporting frontend work as done.
- Read `docs/DESIGN.md` before any UI work. It defines the palette, typography, components, landing page sections, and motion. It wins over the skills on brand decisions; the skills win on craft quality.
- Never copy the reference template's name, copy, icons, emoji, or statistics. Use PitchPrep's own.
- Every component should be mobile responsive

## Backend requirements

- Python, FastAPI, Pydantic v2, async where it helps. Type-annotate everything.
- Configuration through environment variables (pydantic-settings). **Never hard-code model IDs, keys, or URLs.** Model IDs per node come from config.
- LangGraph nodes follow the PRD: Input Parser, Source Collector, link check, Analyst, Matcher, Writer, Verifier, with the capped Verifier retry loop.
- **The Source Collector is a fixed pipeline, not a free-roaming browsing agent.** It scrapes exactly the link the user supplied. Never let a model choose which website to visit.
- All model outputs are validated against Pydantic schemas, with retry on validation failure.
- Every claim in a brief carries source ids. The Verifier sees the source excerpts and any user-pasted text. Unsupported claims are removed and flagged after two revision attempts.
- Wrap Groq and Firecrawl calls with exponential-backoff retries and a concurrency cap (the Groq free tier rate-limits).
- Trace runs in LangSmith. Do not log full secrets or full user-pasted data in plain logs.
- Put tests in `backend/tests` and evaluation code in `backend/evals`. Run `pytest` before reporting backend work as done.

## How to work

1. Read `docs/PRD.md` and the relevant skills, then state a short plan before writing code.
2. Work in small, reviewable steps. Follow the build order in the PRD unless Hamza says otherwise.
3. Match existing conventions and keep changes focused. Do not refactor unrelated code.
4. Ask Hamza when requirements are ambiguous, when the PRD conflicts with reality (for example a model ID that does not exist), or when a change touches the database or deployment.
5. When you finish a task, report: what changed, which files, what you ran (tests, lint, build) and the actual results, and anything you could not verify.
